# AI 转发服务产品设计

状态：开发中的产品设计。已确认规则用于实现与 review；具体数值由商品配置，剩余讨论项见第 9 节。

更新日期：2026-10-08。需求依据为项目负责人的本次讨论，尚未进行外部目标用户访谈或可用性测试。

## 1. 目标与范围

基于 New API 提供多上游、多用户的 AI 转发服务。平台能够按需要分配或固定上游，按可获得的用量证据计算费用，并销售订阅套餐、管理有有效期的积分包。

当前已进入逐轮开发阶段，实施安排见[开发计划](../plans/subscription-billing.md)。具体价格、额度数值、支付渠道、资源权益和运营活动尚未确定。

## 2. 已确认需求

| 编号 | 要求 |
| --- | --- |
| R01 | 管理多个上游平台及账号，支持在可用账号之间负载均衡。 |
| R02 | 支持不负载均衡，使需要利用上游缓存的请求保持在指定上游或会话绑定的上游。 |
| R03 | 支持多个用户，分别管理访问凭证、使用记录和费用归属。 |
| R04 | 综合正常回执、缺失回执、流式中断和失败重试计费，不能把估算用量包装成准确回执。 |
| R05 | 支持收费订阅套餐；同一套餐可配置多个使用额度限制，例如 5 小时、1 周和整个套餐周期。 |
| R06 | 当前月套餐按付款成功起连续 30 天计算有效期；5 小时、周额度从用户开始使用时计时，不按自然日、自然周统一重置。 |
| R07 | 套餐可关联自定义权益标签，后续可以由其他系统把标签映射为资源权益。具体权益暂不定义。 |
| R08 | 每笔积分包或充值包都具有有效期，包括加油包、签到奖励和运营赠送。 |
| R09 | 消耗积分时按照到期时间排序，最先到期的最先消耗。 |

“5 小时”是套餐内的额度窗口，不是单独销售的 5 小时套餐。周套餐可以作为将来可配置的套餐类型，当前不要求推出此商品。

### 2.1 怎样判断计费准确

准确性分别检查用量、价格、额度和账务：可信回执按对应协议计算；缺失字段如实标为估算或未知；费用按已锁定的规则计算；同一消费不重复扣款，发放、扣减、返还和失效都能核对。账务准确不代表网关能获得供应商从未提供的真实用量。

套餐售价是购买权益支付的金额；请求计价是计算该次用量的规则；套餐窗口记录该次使用占用了多少额度；积分包扣款是实际从储值余额支付的数量。这四项分别记录。套餐内一次使用即使计入三个窗口，也不代表收取三次费用，或必然再从积分包扣款。额度沿用 New API 的费用积分单位与模型计价；支付来源按 §7.3 分别核算。

## 3. 核心概念

| 概念 | 含义 | 时间起点 |
| --- | --- | --- |
| 上游账号 | 实际接收模型调用的一套供应商访问配置 | 不涉及套餐计时 |
| 用户 | 平台识别和结算的使用方，可持有多个 API Key | 不涉及套餐计时 |
| 套餐定义 | 售价、期限、额度规则和权益标签的配置 | 不直接计时 |
| 用户订阅 | 用户购买后生效的一份套餐权益 | 付款成功时间 |
| 额度窗口 | 一段时间内允许使用的额度，例如连续 5 小时或 7 天 | 首次符合计量条件的使用 |
| 积分包 | 一笔有来源、有剩余数量、有到期时间的积分 | 该笔积分发放时间或指定生效时间 |
| 请求账单 | 一次逻辑调用的用量、费用、支付来源和调整记录 | 请求发生时间 |

套餐的有效期、额度窗口和积分包的有效期分别管理。窗口重置不延长套餐；购买套餐不自动延长已有积分包；退款不自动延长积分包。

## 4. 上游路由与多用户

### 4.1 路由模式

平台提供以下目标行为，具体配置入口由开发计划确定：

| 模式 | 行为 | 上游不可用时 |
| --- | --- | --- |
| 负载均衡 | 从允许的上游集合中按配置分配请求 | 按明确的重试策略处理 |
| 严格固定 | 请求只允许使用指定上游账号 | 返回不可用，不偷偷改走其他上游 |
| 会话优先绑定 | 同一会话尽量使用同一上游账号 | 仅在策略允许时换上游，并记录切换 |

负载均衡只能分散负载，不能承诺消除 429。多个凭证可能共享供应商的限额，单次调用消耗也可能不同。重试次数、退避和可用渠道需要共同配置。

缓存绑定应覆盖实际使用的账号凭证；固定供应商名称或渠道 ID，但渠道内部仍轮换多个账号，不能视为严格固定账号。平台不保证供应商缓存一定命中。

用户可以拥有多个 API Key，但同一用户订阅的窗口用量必须汇总，不能通过新建或切换 Key 重置额度。上游账号只向有管理权限的人暴露；路由配置必须保持用户的可用模型和上游权限约束。

### 4.2 重试与费用归属

一次客户端调用对应一份逻辑请求账单，各次上游尝试分别记录。重试不能重复预占或重复向用户扣费。供应商可能已经对失败尝试收取费用，因此上游成本与用户收费分别记录；失败尝试是否向用户收费见第 9 节。

已经向客户端发送输出后，不能直接从头换上游重试并拼接成同一份结果。上游已接收请求但结果未知时，也不能宣称重新调用没有重复生成或重复成本；网关账务防重复与供应商执行防重复分别处理。具体允许重试的阶段纳入 D11。

## 5. 订阅套餐与额度窗口

### 5.1 套餐有效期

- 首次购买从核实付款成功时生效，当前月套餐有效期为连续 30 天，不等同于自然月或加一个日历月。
- 同套餐任何时候都可续费：尚未到期时，在当前到期时刻增加本次购买的期限；已经到期时，从这次核实付款成功时重新起算。用了一半再续一个月，剩余有效期为原剩余半个月加新购 30 天。
- 提前续费不重置当前 5 小时、周窗口，不立即新增一份可同时消费的月额度。每次购买的价格、额度及标签仍保存各自版本；后续期限按对应购买合同接续，不能用新版本覆盖正在享有的旧权益。
- 不同套餐沿用 New API 多订阅能力；本次不新增自动升级、差价换档或自动续费。
- 延迟收到付款通知时，应使用核验后的真实付款成功时间，不能以通知处理时间延长套餐。
- 时间区间采用左闭右开：到期时刻起即不可再发起使用该权益的新请求。
- 套餐到期后，即使额度窗口还剩时间或额度，也不能继续使用套餐权益。
- 套餐支付失败不创建有效订阅；重复付款通知不得重复开通同一订单。

### 5.2 多窗口限制

同一用户订阅可以同时约束多个独立窗口，例如“5 小时最多使用 A 额度”和“7 天最多使用 B 额度”。如果配置了整个 30 天的累计上限 C，每次使用也同时受 C 约束。

同一次套餐消费同时计入所有适用窗口，而不是在窗口之间分摊费用。任意一个窗口不足，该次请求不能继续从这份订阅获得额度。

已确认（2026-10-08）：采用使用时启动的周期窗口。第一次使用启动 5 小时和周窗口；到期后在下一次使用时开启新周期，窗口内请求不推动结束时间。每次请求不重新统计过去 5 小时或 7 天。

实现沿用 New API 的费用积分计量和调用准入入口：本地拒绝且未调用上游的请求不算开始使用；并发请求共享同一窗口代次，失败释放不能重置其他请求已经使用的窗口。具体候选预占、提交和释放属于技术设计，必须用行为测试证明，不再作为商业启动门禁。

### 5.3 时间示例

以下均为北京时间。用户在 2026-10-07 10:00 付款，2026-10-09 14:00 首次使用：

| 项目 | 开始 | 结束 |
| --- | --- | --- |
| 30 天套餐有效期 | 10 月 7 日 10:00 | 11 月 6 日 10:00 |
| 第一个 5 小时窗口 | 10 月 9 日 14:00 | 10 月 9 日 19:00 |
| 第一个 7 天窗口 | 10 月 9 日 14:00 | 10 月 16 日 14:00 |

按已确认规则，10 月 9 日 19:00 后没有使用，就不开启新的 5 小时窗口。10 月 10 日 09:00 再使用时，新窗口为 09:00 至 14:00；原周窗口继续累计。

额度继续使用 New API 的费用积分：不同模型按原有价格换算，同一订阅允许的模型和多个 API Key 共享额度，不新增 Token/调用次数两套量纲。模型访问范围沿用现有权限配置。

### 5.4 购买、变更与失效

套餐下架只影响新购买；已购买用户保留购买时的价格、额度和标签。创建订单时锁定套餐版本、售价、币种和期限，订单有效期内按合同核验付款；延迟通知不能延长已付款权益。

本系统不提供用户自助退款、自动现金退款、按剩余天数自动计算退款或自动返还购套餐积分。管理员可以手动取消权益，取消后拒绝使用该权益的新请求，标签立即失效；已经获得预占的请求保留原来源与历史，按原请求结算规则处理。订阅和订单不能硬删除后丢失账务依据。

需要退钱时，由管理员在系统外自行处理，金额和付款方式由管理员决定。系统只负责权益状态及操作审计，不承接退款付款流程。请求未用预占释放、已结算请求有依据的费用修正仍保留，见 §7.4。

## 6. 自定义权益标签

套餐支持管理员定义的权益标签；用户购买后，其有效订阅可提供对应标签及失效时间。用户或接入方可以据此进行资源映射，标签配置和生效依据必须由服务端管理。

本轮只定义标签承载和查询能力，不凭空设计具体资源产品。标签本身不自动授予外部资源权限；实际资源系统需要校验订阅状态、标签和用户身份。

已确认（2026-10-08）：购买时保存套餐版本与标签快照。管理员编辑商品不会改变已购买权益；需要停止某个用户权益时使用明确、可审计的取消操作。查询按各份有效订阅返回标签、版本与有效期，不把不同套餐的同名标签悄悄合并为新权限。

## 7. 有效期积分包

### 7.1 发放与展示

每笔充值、加油包、签到奖励、活动赠送分别形成积分包，至少记录用户、来源、发放数量、生效时间、到期时间和剩余数量。所有新发放包必须有明确到期时间；具体有效期由商品或活动配置。

签到只是来源示例，本轮不要求开发完整签到活动。兑换码的兑换截止时间与兑换后积分的到期时间是两条独立规则。

用户能看到总可用积分、各包剩余数量和到期时间；总可用积分不包含已到期、未生效或被其他请求预占的积分。管理员能按来源和请求查看发放、消耗、释放、到期和调整明细。

### 7.2 消耗顺序

从已生效、未到期、允许用于本次消费的包中，按到期时间升序消耗；到期时间相同，建议按发放时间、包 ID 排序以获得稳定顺序。一笔请求允许跨多个包消耗，不能因为最早到期的包余额不足就跳过它。

示例：签到包剩 30 分、10 月 12 日到期；充值包剩 100 分、11 月 6 日到期。消费 50 分，应扣签到包 30 分、充值包 20 分。

到期检查发生在每次消费决策中，不能仅依赖定时清理。一个包已到期但清理任务尚未运行，也必须立即停止可用。

### 7.3 与订阅的关系

已确认（2026-10-08）：套餐和加油包是两份独立购买的资源，各自保存额度、使用记录与有效期。例如月套餐与半年有效的加油包同时持有；套餐到期不使加油包到期，加油包消费不延长套餐、不重置套餐窗口，也不扣套餐已用量。

支付来源继续复用 New API 的订阅优先、钱包优先、仅订阅、仅钱包偏好及允许钱包接续的配置。套餐额度不足时，允许的加油包可以独立支付；这叫切换支付来源，不叫突破套餐限制。整笔请求按选定来源支付，不新增套餐与积分拼单产品。套餐仍须通过自己的全部窗口检查，包仍须通过自己的期限和用途检查。

余额购买套餐沿用已有能力，参与的包由商品/来源用途配置决定，先到期先用只在允许购套餐的有效包内执行。各来源具体默认期限、用途不猜测，管理员显式配置即可开发和验证。用户之间不允许转赠或转移积分；邀请奖励转入用户自己的钱包不属于跨用户转赠。

### 7.4 三种返还不能混用

| 操作 | 处理对象 | 正确性要求 |
| --- | --- | --- |
| 释放预占 | 尚未结算的积分或窗口占用 | 回到原来源，已过期部分不能重新可用 |
| 请求账单退还或补差 | 已结算的请求费用 | 关联原请求和分配明细，防止重复返还，不改写原始证据 |
| 管理员取消权益或核查支付撤销 | 套餐、充值订单及其发放权益 | 停止新使用并保留已用、在途和原支付记录；不执行现金退款或自动返还购买价款 |

运营补偿是另一次有原因、有期限的发放。是否给予补偿、给多少，由商品规则或管理员明确决定，不暗中延长原包。

### 7.5 跨到期结算与余额不足

有效期内成功预占的积分可以在原包到期后结算该请求；未使用部分释放回原包，已经到期则计入失效，不恢复可用、不延长期限。追加预占只使用当时合法有效的来源。此规则于 2026-10-07 确认，本次继续有效。

2026-10-08 最新确认：不提供用户欠款、授信或充值后自动偿债；余额/额度不足就停止继续付费使用，积分包不扣成负数。此结论替换此前 D07 的“记欠额、后续充值偿付”方案。已实现的欠款生成与自动偿付路径需要调整，不能因旧代码已提交就保留旧收费规则。

最终回执高于预占且合法可用资源不足的异常，不能伪造费用为零、不能向未来充值追扣。负责人已在本次讨论明确采纳：只扣合法可用额度，超出部分由平台承担，作为未收取费用记录；能监测到途中不足时停止继续生成，充值后不追扣。未知用量继续明确标为未知，不能形成猜测扣款。

### 7.6 发放与开发数据范围

每个新积分包必须显式配置到期时间及用途，兑换码自身的兑换期限与到账积分期限分别保存。发放、重复通知及运营补偿都遵循来源防重；补偿是另一次有原因、有期限的发放。

项目尚无真实用户和历史余额，本次从新部署、新账户开发。取消历史余额逐包重建、旧欠额导入、旧订阅商业迁移和灰度用户切换的产品工作。数据库新建、重复启动、结构兼容及故障恢复仍按项目工程要求验证，不依赖真实用户、生产付款账号或生产上线条件。

## 8. 用量计量与费用解释

| 场景 | 目标处理 |
| --- | --- |
| 获得可信完整用量 | 按真实输入、输出、缓存等明细和价格快照计算 |
| 只有部分用量 | 保留已知字段，缺失部分单独估算并标注来源 |
| 上游不给用量 | 按能观察到的输入、输出估算；无法估算的项目标为未知 |
| 客户端中断流式输出 | 沿用 New API 关闭上游流及现有用量估算；保留已知字段，明确标记缺失项 |
| 上游失败、超时或重试 | 分别记录各次尝试；退款和收费依据费用证据及已确定的商品规则 |
| 后续取得更可信用量 | 以关联原账单的调整记录补差，不覆盖原始证据 |

缓存读取、缓存写入、输入、输出以及实际发生的工具调用应按供应商语义区分，避免重复计量。不能在没有回执时推测命中了多少缓存，或把不存在的工具费用直接补进账单。

供应商回执也可能错误：异常数值需要校验，并保留原始证据。用户收费与上游成本分别计算，估算不能承诺与供应商最终账单完全一致。无需为每笔调用都能取得后续回执作保证；不能核实的账单应保留估算或未知状态。

具体账户模型、并发约束和结算过程见 [账户与计费设计](accounting.md)。

### 8.1 沿用现有计费与路由的依据

### 8.2 参考逻辑的实际边界

额度不足的新请求在调用上游前拒绝。在途请求沿用 New API 的“预占、按实际用量结算、释放未用量”生命周期，保持原来源和窗口代次；不能因套餐到期或管理员取消就清掉已取得的预占。可以监测的增量不足停止继续生成，已经发生但最后才获得的费用仍需要如实记录。

关闭网关连接无法保证供应商瞬间停止计费；本系统不会因此把用户扣成负数，也不能伪称所有供应商都有实时扣费回执。完全未知的请求保留核查状态；确有来源的零费用正常释放。费用调低回到原包，到期部分失效，不附带自动现金退款或延长积分期限。

## 1. 交付范围

在现有 New API 上完成统一账本、独立到期的积分包、多个额度窗口共同约束的订阅，以及可解释、可恢复的请求结算。复用已有用户、渠道、支付、模型适配和计价能力。

用户最终可以查看套餐有效期、各额度窗口、积分包余额及到期时间、请求扣款来源与用量依据。管理员可以配置套餐和积分有效期，管理权益标签，处理有依据的账单调整。

改造跨越数据库模型、结算服务、管理接口、Redis 缓存和前端，属于中到大型账务改造。现阶段按里程碑安排，不承诺缺少业务决策和完整测试基线支撑的日历工期；P0 完成后按实际任务拆分估算。

具体资源产品、自动续费/自动升级、新供应商适配、完整运营活动系统、跨用户转赠、用户欠款、自动现金退款和历史用户商业迁移不在本计划交付范围。已有签到、邀请奖励等发放入口必须接入新账本。

### 1.1 协议与兼容范围

- 首批完整链路验收覆盖 OpenAI Chat Completions、Responses、Claude Messages 的文本请求，包含流式和非流式、输入输出与缓存计量。
- 图片、音频、实时会话、异步视频和任务插件等已有收费路径纳入钱包入口盘点与兼容回归，沿用各自计量语义，不套用文本估算规则。
- 新账户只允许使用已验证接入新账本的路径。尚未验证的路径应在消费前明确拒绝，不能回落到旧余额扣款；首批对外开放的模型和协议清单在 P0 记录，缩减目标范围需另行确认。
- `relaykit/` 继续只负责协议类型和转换；账户、数据库和结算规则放在主模块。

路由调查和页面契约可以提前开展；生产账务切换必须等到相关阶段共同验收。P1 建表时就验证迁移，P6 再演练完整发布流程。

开发验收采用逐步接通的真实链路：先“发包 → 文本请求预占 → 用量结算 → 包明细查询”，再加入“多窗口订阅 → 同一请求结算”，最后补偿和恢复。每条链路通过后再扩展入口，不等到 P5 才首次验证真实请求；页面可先使用现有入口或管理 API 验证。

### 2.1 开发轮次估计

按当前设计，安排 **12 轮开发与验收，并预留 2 轮处理回归和迁移问题**。全部完成按 12–14 轮规划；这是当前范围的工程估计，不是工期承诺。P0–P6 是能力阶段，轮次是能独立检查和提交的工作批次，一个阶段可以分多轮完成。

一轮包含明确契约、失败测试、实现、受影响回归和结果审查，可能需要多次对话和多个提交。代码写完但必要数据库验证、业务规则或恢复用例尚未完成时，该轮仍未验收。这里的“全部完成”指本计划范围及 A01–A24 验收完成，包含迁移与发布准备；生产部署按实际发布安排执行。

| 轮次 | 对应阶段 | 本轮交付与验收重点 |
| --- | --- | --- |
| 第 1 轮 | P0 | 收支与协议清单、完整测试基线、三数据库/Redis 环境与 CI 矩阵；确认第 2–4 轮依赖的规则 |
| 第 2 轮 | P1 | 积分包、账务记录及数据库约束；发放、防重、到期、用途筛选、跨包分配和并发守恒 |

| 第 4 轮 | P2 | 全部充值、兑换、签到、邀请、转入和管理员调整；商品发放/撤销与操作核查，退款付款不在系统内执行 |
| 第 5 轮 | P2 | 图片、音频、实时和异步任务等已有收费入口接入，按首轮清单验收；预占追加、退款与分步失败处理 |

| 第 8 轮 | P3 | 多窗口联合限制、首次使用启动、多 Key 共享、旧代次结算、续费及订阅/积分编排；完成 P3 验收 |
| 第 9 轮 | P4 | 字段级用量证据、价格与估算版本、重试/断流费用、原账单补差、未知与平台未收取费用处理，完成计费解释链路 |

每轮同时交付自己的接口契约和必要测试。第 3 轮已有完整消费链路，第 7–8 轮加入订阅链路，第 11 轮形成完整使用界面，第 12 轮满足整体交付条件。必要的防重与恢复状态从第 2–3 轮就建立，第 6 轮集中做跨进程恢复验收；任何一轮单独完成都不作为生产账务切换依据。

本估计假设 D01–D12 在对应轮次前确定、测试环境可用、已有协议和付款渠道按当前范围复用。若改变额度量纲、改成严格滚动窗口、扩大商品退款自动化范围，或开发数据出现结构兼容问题，需依据新增失败案例重排轮次；不能删掉三数据库、故障恢复或迁移验证来维持数字。

第 1 轮结束时复核轮次，之后每轮只根据实际新增范围和验收结果调整。全部验收提前完成则不强行使用预留轮次；预留用完仍有必要验收未通过时，继续处理并如实更新计划。

### 4.2 数据约束

模型最少需要表达以下信息；建表时确定 GORM 字段、索引长度和跨数据库约束，不能仅凭此表声称数据库兼容。

| 记录 | 必要字段与约束 |
| --- | --- |
| 积分包 | 用户、来源类型及业务 ID、发放量、生效/到期时间、余额分量；来源事件防重复，按用户和到期时间查询 |
| 请求账单 | 服务端生成的逻辑请求 ID、用户、价格及商品规则快照、结算状态；同一次网关内部重试复用 ID；区分参考计价、窗口用量和实际积分扣款 |
| 账务操作 | 请求或发放事件、操作类型、操作 ID、输入摘要、结果；唯一操作重复调用返回原结果，不同输入复用同一 ID 应拒绝 |
| 预占分配 | 操作、积分包或窗口代次、预占/结算/释放量；能逐笔回溯，不通过当前余额猜来源 |
| 套餐版本与订阅 | 不可变规则版本、锁价订单、付款成功时间、有效期、标签快照及终止关联；同一订单不重复开通 |
| 窗口实例 | 订阅、规则、代次、起止、上限、已结算与预占量；同一有效代次不得因并发请求重复创建 |
| 上游尝试与证据 | 逻辑请求、尝试序号、内部账号标识、结束原因、字段级用量来源、用户费用和上游成本；不保存可用凭证 |
| 执行资格与恢复待办 | 所有者、租约、执行代次及未完成步骤；条件更新取得资格，迟到旧执行者不能提交 |
| 购买退款与权益撤销 | 原订单、防重退款 ID、管理员操作依据、关联包/订阅、已用和预占处理；保留历史不直接删账 |

积分使用有边界的整数，金额换算复用 [common/quota_math.go](../../common/quota_math.go)；不通过浮点累计积分。时间统一保存为服务端 UTC 时间戳，窗口比较采用左闭右开；页面按用户时区显示。

同一业务操作涉及的账本、来源分配和窗口修改尽量在主数据库同一短事务中完成。各步骤按固定顺序取得账户与来源的并发控制；MySQL/PostgreSQL 使用现有 `lockForUpdate`，SQLite 采用能经并发测试验证的事务与条件更新。外部请求不置于长事务内。

新账本启用后，`user.quota` 和 Redis 只能作为兼容汇总或缓存，不能在账本失败时充当另一份可独立消费的余额。过期会使缓存失真，因此准入必须核实有效期和权威余额；缓存失效可重建，不能恢复已被占用或已到期的额度。

关闭新账户的大余额信任旁路；无限额 API Key 不免除用户账本和套餐窗口检查。窗口单位与包积分分别表示，依据[账户核账规则](../design/accounting.md#3-必须保持的正确性)核对所有分量，平台未收取费用独立记录，不扣成负包。请求与账户分别存储规则版本及并发版本，避免把商品版本与执行资格混为一项。

### 4.3 接口与状态约定

内部按发放、预占、追加预占、结算、释放、调整六种业务操作组织。入口接收稳定业务 ID、用户、规则快照及必要数量；返回持久化结果和来源明细。客户端随意提交的请求 ID 不直接作为跨用户防重依据；客户端重新发送是否为同一业务调用需单独定义，不能和网关内部重试混同。

请求至少区分已创建、已预占、执行中、待结算、已结算、已释放、待核查。超时扫描只负责找出未完成操作；没有费用依据时不能直接全退。后续调整关联原账单，以新增操作保存，原始证据不覆盖。

| 管理能力 | 接口安排 |
| --- | --- |
| 套餐编辑、购买、查看订阅 | 扩展现有 `/api/subscription` 路由下接口，增加版本、窗口和标签；旧字段兼容规则在 P3 写入接口测试 |
| 用户积分包与账务明细 | 在现有用户 self 路由下新增查询接口，返回分页、包有效期、可用/预占等分量和服务器时间 |
| 用户窗口与权益查询 | 自助查询返回窗口起止、上限、已用、预占、可用及权益失效时间；后端过滤无效权益 |
| 管理员发放和调整 | 新增有权限校验的变更接口，要求原因和防重操作 ID；禁止任意覆盖一个总余额 |
| 请求账单 | 扩展现有使用记录查询，关联用量来源、实际扣款包、窗口代次与调整；供应商成本和内部账号仅管理员可见 |

新增接口的最终路径、字段和错误码在所属阶段实施前写入仓库现有 OpenAPI 文档及契约测试。错误至少区分窗口不足、积分不足、权益到期、参数冲突和账务待处理；沿用现有 API 响应外形，页面不能把业务失败展示为成功。

### 4.5 已实现的积分包核心契约

第 2 轮的 `model/credit_pack.go` 提供以下内部接口。它们接受可信服务器时间，尚不直接暴露给客户端，也不自动启用新账务账户。

- `GrantCreditPack(db, CreditGrant, now)` / Tx 版本：用户必须存在；来源类型 1–32 字节、来源业务 ID 1–128 字节且非全空白；正整数积分不超过 `common.MaxWalletQuota`；生效早于到期，时间为正且 JavaScript 安全整数。用途必须明确选择 API（1）、购买订阅（2）或两者（3）；各来源用途和期限由管理员显式配置。
- `ReserveCreditPacks(db, CreditReserve, now)` / Tx 版本：请求 ID 非空且不超过 128 字节；金额为 0 到上述上限；单次用途为 API 或购买订阅。按到期、发放时间、ID 升序分配；不足或任一步写入失败时全部回滚。
- `ListCreditPacks(db, userID, now)`：内部账户查询投影；包到期的未分配量展示为失效，预占保留，未来生效量仍属未分配。后续公开 API 必须分页并提供可消费状态，不能将投影对象保存回表。
- 发放以用户和来源事件防重，预占以用户和服务端逻辑请求防重。稳定 ID 的摘要与输入摘要分别存储；相同输入重放返回原提交结果，数量或规则变化返回 `ErrCreditOperationConflict`。返回值是原操作快照，当前状态另查包，不拿历史快照当余额。
- 每个包保持 `Issued = Available + Held + Spent + Expired + Revoked`，各分量非负且有界；未到期未分配量和全部预占量合计受钱包上限约束。账户行写锁先于读包，SQLite 也以条件写入取得写事务；所有包变更参与同一串行点，不依赖 Redis 锁。
- 本轮表约束保护操作、分配、流水的唯一性和字段非空；数量/守恒由受控事务验证，不依赖 MySQL 5.7 不执行的 CHECK。迁移只加表，旧总余额保留，不伪造旧包历史。

预占不代表已经消费。第 3 轮补齐如下生命周期；发放入口、途中追加预占、调整、撤销与到期登记在后续轮次完成，业务冲突或余额不足不能回落为旧钱包扣款。

### 4.6 已实现的请求结算契约

- `User.AccountingVersion`：0 为旧模式，1 为新积分模式。数据库迁移保留旧用户为 0；单有积分账户或包不启用新模式。本项目从新部署开始，不开发历史用户切换工具；新账户启用契约和防旁路由第 12 轮完整验收。
- `BeginCreditRequest`：主库同一事务写入服务端请求 ID、初始价格/表达式快照、来源预占及 Key 额度。请求费用沿用单次 `MaxQuota` 上限。主库读取 Key 的真实归属和无限额标识；无限额只解除 Key 上限，不能跳过积分包检查。大旧余额、缓存和零预估都不能绕过新模式；合法余额不足时拒绝新付费请求，平台未收取费用不阻断有新资源的使用，明确免费请求仍可记录。
- `MarkCreditRequestSubmitted`：发出上游请求前持久化提交标记；写入失败时不发送。当前接通 OpenAI、Anthropic 的 HTTP 文本入口（Chat/Completions、Responses、Claude Messages）；图片、音频、实时、异步及其他运输方式尚未接入时先拒绝。只用订阅、订阅优先且已有订阅的账户不会被静默改成积分付款，等待第 8 轮接通订阅。
- `FinishCreditRequest`：先在短事务中保存唯一结算/释放意图，再在资金事务中完成来源和 Key 调整。资金写入失败留下 `pending` 及原预占；重启后可重放同一意图。结算与释放互斥，改变结果或费用的重放返回冲突。同金额结算也必须关闭持久化预占，不能因差额为零跳过。
- 原预占按原 FEFO 顺序结算；到期后的未用量归入失效，仍有效则返回原包。实际费用超过预占时，以当时合法来源和有限额 Key 的剩余量补扣，剩余不足由平台承担。包、有限额 Key 均不透支；请求保留 `Actual/Charged/Uncollected`，用户用量统计和收费日志记录真正扣款，参考费用另列。
- 充值只发放本次积分，不偿付以前的平台未收取费用。撤除旧 `CreditDebt` 与自动偿付代码，补余额不足、超预占、Key 上限、充值不追扣、防重及核账用例。此项按 2026-10-08 最新 D07 在需求校正轮补完，不把需求变化记作原设计的 bug。
- 未发送请求可以释放。已发送但结果不明、非明确免费且实际为零的请求保留预占并标为 `review`，不能当作零费用退款。字段级证据、合理的真正零费用、断流估算、恢复工作器和独立日志待办分别在第 9、6 轮补齐；本轮不声称全部证据计费已完成。
- 价格快照记录初始预估规则，不改变现有表达式及自动分组重试语义；实际尝试的路由、价格和用量证据由第 9–10 轮补齐。查询、恢复、调整只能通过受控事务，不能直接保存查询投影或覆盖余额。

### 4.7 第 4 轮发放与退款核查契约

本轮针对新积分账户接入现有发放入口；旧账户保持旧行为，通用用户编辑不能修改账户模式或覆盖新账务余额。新账户的管理员增减/覆盖旧接口明确拒绝；正向调整通过限时发包，购买撤销通过人工核查入口保留来源，终局扣回按 D12 确认后执行。

| 来源 | 稳定事件 | 主库原子边界与期限依据 |
| --- | --- | --- |
| Epay、Stripe、Creem、Waffo、Waffo Pancake、人工补单 | 充值订单 ID | 下单保存积分数量、期限、用途快照；完成订单与发包一起提交，充值不偿付平台未收取费用；回调重放只产生一次发放 |
| 兑换 | 兑换码 ID | 代码已使用标记与发包同事务；创建时保存独立积分期限/用途，旧码无快照时必须有明确来源策略；已用代码不可改写或重新启用 |
| 签到 | 签到记录 ID，用户/日期唯一 | 签到记录与积分包/流水同事务；零奖励只记录签到；配置的随机范围先校验，资金失败不留下签到成功记录 |
| 注册、被邀请、邀请人 | 被创建用户 ID，分别带来源类型 | 用户创建与新模式各奖励同事务，OAuth 后处理重放不再发钱；来源策略给出期限和用途；后处理日志不作为资金事实 |
| 管理员/运营补偿 | 管理员填写的事件 ID | 记录真实操作者、原因、明确生效/到期/用途；同事件同输入重放安全，改变数量等输入返回冲突 |

`CreditSourcePolicy` 以来源、正期限、用途和递增版本配置。策略更新必须携带 `expected_revision`，旧版本不覆盖新设置。未确认的默认期限和默认用途不自动填入；具体策略选项及答复状态在产品设计 §7.6。充值积分有效期从本次成功发放开始；月订阅核验付款时刻的规则在第 7 轮实现，不能把这两种时间混为一谈。不同商品的独立策略配置和页面由后续商品/管理轮次扩展。

订单完成先锁定订单状态，SQLite 在读状态前取得写事务，MySQL/PostgreSQL 使用项目统一行锁；发包仍使用账户串行点。Ledger/pack/order 任一步写入失败全部回滚，重试不重发。旧 Scalar 余额和其缓存不会成为新包的第二笔钱。

邀请奖励在新模式直接形成有期限包，不新增领取商品步骤。旧 `AffQuota` 转入接口对新模式拒绝，避免凭空续期；本项目无历史用户迁移。明确禁止跨用户转赠和转账。

退款核查：`OpenCreditReviewCase` 在同一账户事务冻结包的新使用并保存案件；不抹去可用量、已用量、原预占或来源流水。原请求仍可结算其预占。`RecordCreditCashOutcome` 保存追加式现金证据及案件当前状态：相同内容重放不覆盖后来的确认；不同终局结果冲突；未知结果可补充核实。确认必须有外部参考和证据。它不调用支付平台退款、不发现金、不自动扣回或解冻积分；管理员可取消权益，不自动退款或返还商品购买款。已有现金结果仅作为外部处理依据记录，不承接付款或自动补发。

管理 API 与 OpenAPI 记录保持一致：

| 路径/方法 | 角色与 PAT 权限 | 行为 |
| --- | --- | --- |
| `/api/credit/admin/policies` GET/PUT | Root，`option:read` / `option:write` | 读取/按版本配置来源策略 |
| `/api/credit/admin/grants` POST | Admin，`billing:write` | 发放限时包 |
| `/api/credit/admin/reviews` GET/POST | Admin，`billing:read` / `billing:write` | 指定用户分页查询/创建核查 |
| `/api/credit/admin/reviews/cash-outcome` POST | Admin，`billing:write` | 记录已核实现金结果 |

非 Root 管理员只可操作比自身角色低的目标；服务端按主库当前角色、启用状态及包/案件归属再次校验。操作者从已认证身份取得，客户端 `actor_id` 不改变操作者。写操作沿既有 AdminAuth/RootAuth 管理审计及 CriticalRateLimit；面板鉴权使用 Authorization Bearer，刷新 Cookie 不作为这些接口的独立授权。非法输入 400、未认证 401、无权限 403、不存在 404、防重或版本冲突 409、存储错误 500；内部存储错误不返回数据库细节。

本轮权限检查依据 [OWASP ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md) 的 8.1.1、8.2.1–8.2.3、8.3.1–8.3.2，以及 [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 指南。测试验证读写权限分离、过期/撤销、角色降级、伪造操作者、目标归属及重放；这是所改接口的验证记录，不宣称整个项目完成 ASVS 认证。

### 4.8 第 5 轮追加预占与多协议契约

追加预占按请求累计目标额执行，同一目标重放不重复占用。账户、积分包、请求累计额、追加来源记录和 Key 额度在主库同一事务提交；不足时全部回滚。追加只使用追加时合法来源，已过期可用量不能补占。各次预占的原来源记录保持不可变，结算按预占取得顺序消费，剩余返还仍遵守原包期限。第 3 轮没有追加记录的在途请求保留原预占，并在第一次追加时补齐来源关联。

每个协议在开启新账户访问前必须具备发送前的持久化标记和唯一结算入口；不能只删除协议限制便宣称接入完成。图片参数覆盖后先追加再发送，实际数量沿用项目图片载荷计数规则。音频、实时累计用量、异步任务成功/失败及持久化失败逐项验证，异步任务需要持久化关联原请求，不能在轮询时直接改旧钱包。

任务与账单同事务保存关联：原任务编号、区分大小写的摘要、任务表主键、用户和任务类型。完成时重新锁定并核对原任务，主库金额回写与包、Key、请求状态共同提交。任务失败但费用未知时保留预占进入核查，不按失败状态自动全退。实时计量由单个处理循环维护，去重有稳定事件 ID 的完成回执，音频/文本/缓存沿表达式归一化；Responses WebSocket 的复用连接每个请求仍独立标记提交。

中断与失败行为参考 New API，核对结果和改造边界见设计 §8.1。可核实成功消费和资金一致性不依赖上线配置，使用本地三数据库和模拟上游验证。

### 4.9 第 6 轮恢复与核账契约

执行资格属于单个请求，包含服务器生成的所有者、递增代次及租约截止。主库账户锁内取得或续租，活跃租约不得被另一执行者抢走；到期后新代次接管，旧代次的发送、追加、结算、释放及核查写入均拒绝。正常长请求定时续租，租约丢失时取消本地请求；租约不是上游停止或免费凭据。异步提交交接后释放执行资格，后续轮询取得新资格。

恢复分页扫描持久化记录：已有终结意图只重试原意图；未提交请求可释放；已提交且结果不明只转核查；异步任务先按已保存任务状态处理，不能凭超时推算收费。错误、重试次数和下次时间可查询，不删除资金或防重事实。扫描和账务提交均允许多实例竞争。

恢复默认每 30 秒扫描，`CREDIT_RECOVERY_INTERVAL_SECONDS` 可调整；`CREDIT_RECOVERY_MAX_ATTEMPTS` 默认 20 次，超限保存待处理标记，不清除原意图或资金。具体重试错误在主库和管理查询可见。`POST /api/credit/admin/work/retry` 要求 `billing:write`、唯一事件及原因，只重试已知意图或日志；不知道费用的请求不能通过“重试”按钮变成退款或收费。`GET /api/credit/admin/work?user_id=…`、`GET /api/credit/admin/reconcile?user_id=…` 要求当前管理员及 `billing:read`，不返回租约所有者或日志载荷。权限控制复用主库目标角色校验；参照 [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)、[Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) 与 ASVS v5.0.0 V8，验证拒绝默认权限、读写范围及角色降级。

结算主事务更新用户/渠道统计并创建独立日志待办，重放不重复统计。日志库独立事务保存投递标识和日志，响应丢失后查同一标识，不再重复插入；主库待办完成失败只重试确认。非事务日志引擎必须有经过验证的等价防重能力才能自动投递，否则保留可见待办，不冒充成功。核账按一致事务快照核对包守恒、流水分量、预占与分配、请求实际扣款及平台未收取费用，返回具体记录和差量，禁止自动改余额抹平差异。

### 4.10 第 7 轮套餐版本基础契约（开发中）

版本基础先实现管理员显式保存的不可变套餐记录，不开通订阅、不改旧订单或旧订阅、不替 D04/D08/D12 决定商品行为。沿用现有套餐草稿，保存完整服务端快照、摘要、六位小数售价整数、币种、连续 30 天规则、发布人、时间及唯一事件。版本不使用客户端提供的支付结果。

发布请求明确套餐 ID、已看到的草稿摘要、上一版本号和唯一事件；版本号省略或 null 与显式 0 区分。主库锁定套餐后读取当前草稿，草稿已修改或版本已更新则返回冲突，不覆盖其他人的操作。同一事件重放返回原版本，不因为之后编辑而发布不同合同；失败不留下版本或跳号。草稿读取绕过旧缓存。管理员身份取当前主库角色和状态，接口要求 billing 读写范围，客户端不能选择操作者。分页拒绝负数及偏移溢出；适用权限控制参照 §4.9 的 OWASP 指引与 ASVS v5.0.0 V8。基础能力采用当前已经确认的月套餐连续 30 天规则；其他期限不在这里偷偷换算。

`GET /api/subscription/admin/plans/:id/versions` 返回当前草稿摘要、最新版本号和分页版本；`POST` 发布版本。购买与付款、标签格式/快照、续费起止、终止返还和窗口编排继续按设计 §7.7 的明确答复实施，本轮整体尚未验收。

订单与支付事实基础沿用账户设计 §8.3 的约束：主库先保存当前已发布版本、完整合同、整数金额和币种；下单事件按用户防重。期限由服务器明确提供，不设未确认的默认订单期限；重复下单返回原合同，修改草稿不修改已存在订单。新下单必须指向当前发布版本并检查当前上架状态。这一基础阶段不请求外部支付、不发放权益、不扣余额。

支付事实只能由完成验签及支付核查的服务端调用方写入，无客户端“付款成功”入口。保存渠道、稳定事件/交易编号、实际付款人、金额、币种、付款时间及取证来源与摘要，未知量保持未知。缺失事实、金额/币种不符、付款早于订单、付款不在订单期限内及交易已归另一订单均进入可见核查；不把回调接收时间充作付款时间，不根据订单售价猜到账金额。重复事件返回原事实，同事件不同内容拒绝，同时按内容防重追加关联原回执的矛盾观察，与当前订单核查标记一起提交；冲突结果在保存成功后返回，不能因事务回滚抹去核查依据。不同事件的同一交易不能归两份订单。核验成功与权益发放分开，异常记录不被之后的正常通知自动抹掉。开通、续费、标签及退款处理仍待设计 §7.7 定案。

支付日志只记录处理阶段、订单/事件标识与必要请求位置，不打印签名、支付链接令牌、完整正文或查询串。适用 [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) 的敏感数据排除与日志注入控制，以及 [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)；ASVS 版本沿 §4.9 的 v5.0.0。这里只验证受改支付路径，不宣称全项目完成认证。

当前支付入口仍是旧订单流程，以上版本化购买底座尚未连接到真实开通入口。接入前逐渠道完成合同适配，不把“通用事实保存通过”当作支付通道已经交付：

| 渠道 | 已核实的现有实现 | 新入口还需验证 |
| --- | --- | --- |
| Stripe | 外部 Checkout 先于本地旧订单创建；使用 recurring subscription 模式；回调只传金额/币种而未传实际付款时刻 | 本地合同先提交；SKU/币种/计价精度一致；明确单次购买与自动扣款边界；核实付款时刻的渠道来源。[官方 Checkout 字段](https://docs.stripe.com/api/checkout/sessions/object)中的会话创建时间不能当付款时间 |
| Creem | 本地旧订单先创建；签名后读取 order.status/amount_paid/currency；现有完成接口未核对这些金额；币种受全局展示设置影响 | 商品实际价格/币种与合同一致；取证来源和实际付款时刻。现有 DTO 的 created_at/updated_at 含义不能自行认定为付款时刻。[官方字段参考](https://docs.creem.io/skills/creem-api/REFERENCE) |
| Epay | 本地旧订单先创建；签名验证成功状态，发起金额按两位小数格式化 | 到账金额与币种、付款时间、交易编号；合同价格不能被静默截为渠道精度；浏览器返回与后台通知共用防重 |
| Waffo Pancake | 本地旧订单先创建；固定 USD、两位小数覆盖价格；回调校验签名、环境、Store 和 buyer identity | 保存并核对实际 amount/currency；核实 Timestamp 的支付含义，不能直接等同实际付款时刻；保留测试/生产环境隔离 |

取不到渠道付款事实时保留核查，不要求开发者提供生产账号来继续实现或本地验证。税费、优惠、币种兑换和渠道精度必须在发起付款前有一致合同，不能等用户已付款后才悄悄改价；当前底座未声称这些通道适配已经完成。

## 5. 分阶段任务与验收

每阶段按“明确场景与预期 → 编写会失败的行为测试 → 最小实现 → 受影响回归 → 记录证据”执行。新功能缺口不能以测试被跳过、断言放宽或改写预期的方式变成通过。

### P0：建立可用基线

- [ ] 按发放、消费、退款、管理员调整、异步任务建立余额写入清单，记录调用方、业务 ID、事务、缓存与补偿方式。
- [ ] 盘点信任旁路、无限额 Key、零价格、旧预扣清理、订阅硬删除、余额购买套餐，以及旧余额旁路和批量写入，逐项标明新模式兼容方式。
- [ ] 记录首批开放协议及付费入口；核实多 Key 渠道的实际账号选择，确认已有签到等入口。
- [ ] 运行完整现有 Go 与前端测试，区分既有失败、环境缺失和新增缺口；记录提交、命令与结果。
- [ ] 配置真实 SQLite、MySQL、PostgreSQL 和 Redis 测试环境，在 CI 增加相关账务矩阵；缺少数据库配置必须使专用矩阵任务失败，不能静默跳过。
- [ ] 为时间相关测试提供可控时钟，为并发测试使用明确同步点；不以固定 sleep 或随机循环证明正确性。
- [ ] 逐项确认下一阶段依赖的 D 决策，把已确认规则写回产品设计；仅确认下一步依赖，不要求全部商业细节一次定稿。

验收：所有入口均有测试归属；已有失败有原始证据；新旧问题分开记录。此阶段可直接开始，不以所有商业规则一次性定稿为前提。

### P1：建立积分包和持久化账务核心

- [ ] 增加积分包、操作、预占分配和账务记录；先完成三种数据库的新建及重复迁移测试。
- [ ] 实现有明确有效期的发放与防重，支持未来生效和到期立即不可用。
- [ ] 实现先到期先用、跨包原子预占、按来源结算与释放；到期处理与预占处理分别核对。
- [ ] 实现操作输入冲突检查、持久化状态转换和恢复所需查询；重复结算、释放不重复改变余额。
- [ ] 完成尚未生效、释放遇到期、已结算返还、撤销及平台未收取分量的守恒核对，测试调整累计不能超过原扣款。
- [ ] 确定账户并发方案并验证多连接争用；新增数量沿用现有安全上限和溢出检查。

先写失败用例：A07 的 30 + 20 分配；总额不足时全不扣；同到期时间顺序稳定；到期任务未运行也不能消费；同一事件重复发放；两个请求争抢最后一份余额；结算或释放重放。

验收：A07、A08、A11 的积分包部分及 I02–I05、I07、I11 通过。跨到期预占的结果按已确认 D06 验证。本阶段核心可单独验证，尚不启用生产新账户。

### P2：统一所有收支入口与恢复

- [ ] 接入 [充值](../../model/topup.go)、[兑换](../../model/redemption.go)、[签到](../../model/checkin.go)、[用户奖励和转入](../../model/user.go)、[管理员额度调整](../../model/user_quota_adjustment.go)。区分兑换码期限与积分期限。
- [ ] 接入资金来源、计费会话、实时消费、异步任务及失败退款；检查余额购买订阅等非模型消费。
- [ ] 给支付通知、奖励、后台补偿定义稳定来源 ID；付款时间以已验证支付事实为依据，无法取得时按明确异常流程处理。
- [ ] 同主库更新资金、窗口和 Key 额度时优先一起提交；无法一次提交的部分保存待办状态，并在恢复时只补未完成步骤。独立日志库不参与主账本事务，日志失败需要可重放。
- [ ] 新账户的旧余额直接写入点全部改为统一入口或明确拒绝；缓存仅在提交后更新，失败可失效重建。
- [ ] 增加恢复任务及管理员待处理查询，保存最后错误、尝试次数和处理结果；多实例同时恢复也只生效一次。
- [ ] 给恢复接管增加执行代次校验；模拟旧执行者迟到、数据库提交结果不明及独立日志库失败，保证只补未完成步骤。
- [ ] 接入余额购买套餐的跨包扣款与原子订单创建；按 D12 实现商品撤销、稳定核查事件 ID 或明确人工处理路径。

先写失败用例：重复付款通知只发一个包；支付已入账而缓存更新失败；资金提交后 Key 或日志步骤失败；进程退出后重复结算；异步任务重复回调；退款遇到原包到期；管理员重复提交。

验收：A11、A14–A18、A20 的账户部分通过；P0 清单中的每个已开放入口均有接入证据，不存在绕过新账本的备用扣款路径。

### P3：实现多窗口订阅与权益数据

- [ ] 增加套餐规则版本，购买时保存价格、窗口及标签快照；订单防重，月套餐有效期按付款成功后连续 30 天计算。
- [ ] 窗口按用户订阅创建，多个 API Key 共享；首次启动及失败撤销按 D01 执行。
- [ ] 同一次消费原子检查并预占所有适用窗口，费用只记一次；新周期生成代次，旧请求继续关联原代次。
- [ ] 实现已确认支付来源选择、同套餐续费顺延、不同套餐多订阅；不新增自动升级；不能通过重买或切换来源意外绕过限制。
- [ ] 增加标签配置、版本和有效权益查询；保留已有用户分组兼容，明确两者职责。
- [ ] 旧订阅保持原有规则；管理员重置、失效和删除接口不能破坏未完成预占及账务历史。
- [ ] 支付开通遵循锁价订单；覆盖下架、延迟通知、金额不符和重复/乱序撤销。保留支付核查/终止依据，对在途窗口按 D12 处理。

先写失败用例：付款两天后首次使用；5 小时耗尽而周额度仍有；并发首次使用只开一个代次；两个 Key 共用上限；一个窗口失败后其他窗口无扣减；跨重置结算；订阅到期但短窗口尚未结束；重复通知与标签变更。

先写失败用例：完整缓存回执不重复计费；部分回执加输出估算；无回执与真实零用量可区分；非法数量拒绝；断流后进程退出；第一次上游失败后重试；价格中途修改；补差重复执行和执行一半失败。

## 6. 数据迁移与回退

### 6.1 新部署与结构验证

本项目无历史用户、历史余额和旧欠款，不开发商业数据迁移、逐包期限推测或用户灰度切换。第 12 轮验证新部署、新账户启用、重复启动、并发实例、预占/结算中断恢复及防旁路。

### 6.2 开发恢复边界

### 7.3 验证命令与环境

下列命令用于后续实施；实际运行清单见[逐轮证据](development-progress.md)。本地矩阵通过 `make test-db-up` 和 `make test-database` 运行。

```bash
# 仓库根目录：相关现有测试；新增用例并入对应包
go test ./model ./service ./relay/helper ./controller -count=1

# 全量 Go 回归，包含独立 relaykit 模块
make test

# 受影响账务包的并发检查
go test -race ./model ./service -count=1
```

三数据库矩阵必须使用真实实例，覆盖全新建表、旧库升级、重复启动、并发扣款和失败恢复。现有测试使用 `TEST_MYSQL_DSN`、`TEST_POSTGRES_DSN`，固定价格测试另用 `TEST_FIXED_MYSQL_DSN`、`TEST_FIXED_POSTGRES_DSN` 及对应 LOG DSN；P0 明确每组用例读取哪些变量，CI 显式注入，禁止把凭证写入验收文档。Redis 覆盖启用、禁用、断连及重建场景。

```bash
# 在 web/ 目录执行
bun install --frozen-lockfile
bun run test
bun run typecheck
bun run lint
bun run build
```

前端日常迭代先运行受影响文件，合并与发布时执行相关完整检查。根模块构建需先生成 `web/dist`；执行 `GOWORK=off go vet ./...` 和 `GOWORK=off go build ./...`，并在 `relaykit/` 内独立执行相同检查。浏览器测试命令待 P5 实际引入后补充，不预称已有可运行入口。
